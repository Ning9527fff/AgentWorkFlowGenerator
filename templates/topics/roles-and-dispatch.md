# 角色与契约派发

本页供 Architect（与用户对话的主会话）使用：派发 Coder、处理技术异议、组织集成与验收。契约分简版和完整两种。契约类型与审查档位相互独立：契约类型决定契约写多少，审查档位决定审查强度，简版契约不降低审查档位。

## 角色边界

| 角色 | 不做 |
| --- | --- |
| Architect | 不修改可执行代码、测试、数据迁移和运行配置 |
| Coder | 不改变核心决策，不发起审查，不写任务记录 |
| 审查职能 | 不修改代码，不分派其他审查者 |

## 文档改动

- 不属于拆分任务的单次规范或业务文档修改，由 Architect 直接完成。
- 拆分任务中需要按推进门禁审查的文档小任务，写成简版契约派发给 Coder。

## 契约派发流程

1. **冻结决策**：需要长期保留的技术决策写成 ADR，规则见 `.agents/decisions/README.md`。
2. **拆分**：判定任务类型并写入任务记录的“拆分与规划”表，登记每份契约及其依赖。按依赖顺序串行执行，同一时间只有一份契约处于执行中。任务类型决定契约的粒度，也决定推进门禁中“一批”的范围：
   - 细分任务：设计或改动模块共用的基础结构，如公共执行层、公共客户端、公共数据结构。按步骤拆成多份契约，每份契约是一批。
   - 普通任务：在已有基础结构上增加业务能力，如新增一个查询接口。一个完整能力（入口、业务逻辑和测试）通常写成一份契约；确需拆成多份时，这个能力的全部契约是一批。
   - 普通任务执行中发现需要改动基础结构时，Coder 按技术异议提出，由 Architect 把基础结构部分拆为细分任务。
3. **编写契约**：另见 [任务契约](task-contract.md)。先判定简版或完整，写入契约头部并注明依据，再按对应要求填写。
4. **派发 Coder**：分派内容只有 Coder skill 路径和契约文件路径。不转交讨论历史、被排除方案的讨论过程或其他契约。
5. **收回执行报告**：核对契约文件中的执行报告是否齐全。有技术异议时先处理异议，不进入审查。
6. **独立审查**：Architect 担任审查协调者；轻量档未升档时，分派一个单人审查者。分派时附契约文件路径，审查以契约的目标、技术决策和验收标准作为需求依据之一。
<!-- 条件: 轻量升档 -->
   单人审查者报告“需升档”时，先按任务契约专题重新判定契约类型：不再满足简版条件的，改为完整契约并补齐各节，版本号加一，需要补充实现或执行报告的交原 Coder；然后改走审查协调流程。
<!-- /条件 -->
7. **修复与复核**：审查问题连同问题台账交原 Coder 修复。原 Coder 无法恢复时，把契约、执行报告和问题台账交给新的 Coder，并在任务记录中写明原因。出现审查交接专题“停止复核”一节列出的情况时不再发起下一轮，把未决项交用户决定。
8. **推进门禁**：按项目入口的推进门禁执行。用户授予自主推进授权时，另见 [自主推进](autonomous-mode.md)。
9. **集成与验收**：全部契约完成后，Architect 核对模块集成、与 ADR 的一致性和用户需求的验收条件。集成需要修改代码时，作为新的契约派发，符合条件的用简版。在任务记录的“交付”一节写交付报告，填写“度量”一节，交用户 review。

## 处理技术异议

Coder 在契约文件中提出技术异议后，Architect 逐条答复并更新状态：

- **维持原方案**：写明理由，Coder 按原契约继续。
- **修订契约**：修改契约正文，版本号加一，在“修订记录”中写明变更与原因；涉及技术决策时新增或替代 ADR。修订后不再满足简版条件的，改为完整契约并补齐各节。契约已进入审查的，受影响的审查结论需要复核。
- **需要用户决定**：涉及需求范围、对外契约或高风险区域时，向用户确认后再答复；处于自主推进授权下的，按该授权的停止条件处理。

异议未答复前，Coder 不继续受影响的部分。同一事项经答复后 Coder 再次提出异议的，Architect 不再自行裁定，交用户决定。

答复后继续原 Coder（原 agent 或原会话），不新建。原 Coder 无法恢复时，把契约连同异议与答复交给新的 Coder，并在任务记录中写明原因。

## 子 agent 与模型

模型按角色配置，“继承”表示使用主会话的模型。

工具不支持子 agent 时：

- Architect 为每个角色开启新的独立会话，每个会话只加载一个角色的 skill，分派内容与子 agent 相同；无法开启时请用户开启。
<!-- 条件: 档位=标准,严格 -->
- Coder 或审查职能仍无法开启时，不由 Architect 代为实现或审查，向用户说明并停止推进，由用户决定如何继续。
<!-- /条件 -->
<!-- 条件: 档位=轻量 -->
- Coder 仍无法开启时，Architect 可以按契约自行实现并自检，在任务记录中写明原因。这时 Architect 是实现者，不能审查这份改动。
- 没有独立审查的契约（审查者无法开启，或由 Architect 自行实现），推进门禁改为：自检完成后标为“待用户 review”，在任务记录的“交付”一节写明“无独立审查，只有自检结果”，用户确认后才继续下一份。不得声称完成独立审查。
<!-- /条件 -->
<!-- 条件: 轻量升档 -->
- 改动触及高风险区域或不确定是否触及时，以上两条不适用：Coder 或审查职能无法开启时，向用户说明并停止推进，由用户决定如何继续。
<!-- /条件 -->
